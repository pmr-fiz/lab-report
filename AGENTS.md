# AGENTS.md — Lab Report Agent (МТУСИ)

Канонические инструкции для агента (Claude Code, Codex и любой другой).
Этот репозиторий — конвейер, который по тексту лабораторной работы пишет код,
проверяет его запуском в терминале и оформляет отчёт Word строго по стандарту
кафедры.

> Claude Code читает `CLAUDE.md`, Codex — этот файл. `CLAUDE.md` ссылается сюда,
> так что источник правды один — `AGENTS.md`.

## Приём задания (intake)

Пользователь кладёт файл задания (`.docx`/`.pdf`) в папку `inbox/` и указывает
его в чате через `@` (напр. `@inbox/Лаб_3.docx`). Папку и структуру ты создаёшь
сам:

- **Найди файл задания.** Это файл, на который сослался пользователь через `@`;
  если он не указан — возьми самый новый файл в `inbox/`.
- **Определи номер лабы N** из текста задания (ищи «Лабораторная работа №N»
  или «№N»). Если номера нет — возьми следующий свободный (`labs/<N>` + 1) и
  сообщи пользователю выбор.
- **Создай** `labs/<N>/`. Папку `tests/` НЕ создавай.
- **Перенеси** файл из `inbox/` в `labs/<N>/task.docx` (или `.pdf`).
- **Выбери раскладку кода** (см. ниже) и положи файлы данных, приложенные к
  заданию (напр. `works.txt`), рядом с кодом, который их читает.
- Дальше иди по пайплайну ниже — всё записывай внутрь `labs/<N>/`.

**Раскладка кода.**

- **Методичка задаёт структуру проекта** (каталог, имена файлов, `.venv`) —
  воспроизведи её ТОЧНО внутри `labs/<N>/`: тот же каталог, те же файлы и
  столько же, сколько просит методичка, `.venv` создай
  (`python3 -m venv .venv`) и запускай программы из него. Решения заданий,
  которым методичка не назначила отдельный файл, — функциями `task2()`,
  `task3()`, … в главном файле (обычно `main.py`) со словарём номер → функция:
  `python main.py N` запускает одно задание, без аргументов — все.
- **Структура не задана** — `labs/<N>/src/taskK.py`, по одному
  самостоятельному файлу на задание-программу.

```
labs/<N>/                          labs/<N>/
  task.docx                          task.docx
  <каталог из методички>/            src/task2.py ...
    main.py, <модули>, .venv/        report.docx (+ .pdf)
  report.docx (+ .pdf)               EXPLAIN.md
  EXPLAIN.md
```

Больше ничего в `labs/<N>/` не кладём.

## Пайплайн (на каждую лабу, по порядку)

Не пропускай проверку решений в терминале и финальную визуальную проверку отчёта.

1. **Разбор задания.** Задание лежит в `labs/<N>/` как `task.docx` или
   `task.pdf` (в markdown лабы не дают). Извлеки текст:
   `python read_task.py labs/<N>/task.docx` (или `.pdf`). Если у PDF смешался
   порядок строк — открой файл и прочитай сам. Выдели: цель, список заданий,
   тип каждого (вопросы / программа), контрольные вопросы в конце (если есть).
2. **Решение.** Код — в раскладке, выбранной при приёме задания (структура из
   методички или `src/taskK.py`), см. «Правила для кода решений». Только
   стандартная библиотека Python, если задание не требует иного.
3. **Проверка в терминале.** Тестовые файлы НЕ создавай (никаких `tests/`,
   `test_*.py`, `conftest.py`). Вместо этого:
   - запусти каждое решение (`python main.py N` или `python src/taskK.py`) и
     прочитай вывод;
   - корректность проверь прямо в терминале разовым скриптом через heredoc
     (`python - <<'EOF' ... EOF`): импортируй функции и классы решения, сверь с
     полным перебором или стандартной реализацией на маленьких входах, проверь
     граничные случаи;
   - нашёл ошибку — чини код и прогоняй заново. К отчёту — только когда все
     проверки проходят.
4. **Вывод.** Вывод программы в отчёт идёт РЕАЛЬНЫЙ, из запуска. Не выдумывай.
   Объём — не больше одной страницы (см. «Правила для вывода программ»).
5. **Объяснения.** Для задания-программы — объяснение в отчёте (состояние,
   переход, сложность и т.п.). Для задания-вопросов — ответ и обоснование по
   каждому пункту. Все пояснения к коду живут здесь и в `EXPLAIN.md`, а не в
   комментариях. `labs/<N>/EXPLAIN.md` — подробный разбор всей лабы для
   самопроверки: как устроен каждый файл, что делает каждая функция, какие
   проверки прогонялись и с каким результатом.
6. **Отчёт.** Собери `.docx` ТОЛЬКО через `report_builder.py` (см. ниже).
   Не верстай оформление руками из промпта. Скрипт сборки запускай из
   терминала (heredoc или временный файл во временной папке, не в
   `labs/<N>/`); вывод берётся из реального запуска каждого задания. Если
   объяснения цитируют числа из вывода (замеры времени), сохрани вывод один
   раз во временную папку и собирай отчёт из него, чтобы текст и вывод
   совпадали.
7. **Проверка.** Отрендери `.docx` в PDF и посмотри на него (см. «Проверка»).
   Сверь титульник, шрифты, отступы, блоки кода и вывода со стандартом.
   Готово — только после этого.

## Правила для кода решений

- **Никаких комментариев и докстрингов.** Ни шапки модуля с названием задания
  и описанием алгоритма, ни `"""..."""` у функций, ни `#` в строках. Код
  должен читаться за счёт имён; всё объяснение — в отчёте и `EXPLAIN.md`.
- **Никаких модулей сверх нужного.** Не выноси исходные данные и общие
  помощники в отдельные файлы (`inputs.py`, `lab_data.py`, `common.py` и т.п.).
  Файлы создаются только те, что требует методичка, либо по `taskK.py` на
  задание. Массивы, строки и параметры из текста задания пиши прямо в коде
  задания. Приложенный файл данных читай рядом лежащим путём
  (`Path(__file__).with_name("works.txt")`).
- В раскладке `src/` каждый `taskK.py` запускается сам по себе и ничего не
  импортирует из других файлов лабы. В раскладке из методички модули проекта
  импортируются друг из друга так, как задумано методичкой.
- Строки кода — не длиннее 86 символов (иначе переносятся в блоке отчёта).
- Номер файла = номер задания в тексте работы. Если в задании повтор или
  нестандартная нумерация («6.1», два «Задание 7») — используй следующий
  свободный номер и скажи об этом пользователю.

## Правила для вывода программ

- **Не больше одной страницы отчёта:** до ~45 строк и не шире 86 символов.
- Большие данные не печатай целиком: итог + короткий фрагмент (первые/последние
  несколько элементов, угол таблицы, одна строка на запись), длинные списки
  переноси через `textwrap`.
- Если задание просит «вывести всё» (расписание, таблицу, маршрут), а это не
  влезает в страницу — выведи компактно (одна строка на элемент, без
  описаний/пустых строк) или сводку плюс фрагмент, и объясни сокращение одной
  фразой в отчёте.

## Стандарт оформления (реализован в report_builder.py — придерживайся его)

- A4; поля: левое 3 см, правое 1.5 см, верхнее/нижнее по 2 см.
- Основной текст: Times New Roman 14 pt, по ширине, красная строка 1.25 см,
  интервал 1.5.
- Заголовки («Цель работы:», «Задание N», «Решение:», «Контрольные вопросы:») —
  полужирные.
- Код — настоящим текстом на тёмном фоне с подсветкой (НЕ скриншот);
  вывод программы — отдельным тёмным блоком под кодом.
- Формулы — стилем Cambria Math (если понадобятся).

## Как собирать отчёт (report_builder.py + code_block.py)

Модули готовы и протестированы — используй их, не переписывай стандарт.

```python
import report_builder as rb

doc = rb.new_report()
rb.title_page(doc, lab_number="4", lab_title="Название работы")
# department/group/student_name НЕ переданы -> останутся плейсхолдеры {{...}};
# либо прочитай config.json и передай значения в title_page(...)

rb.goal(doc, "Текст цели...")

# задание-вопросы:
rb.task_heading(doc, "Задание 1. ...")
rb.body(doc, "Условие...")
rb.answer_items(doc, [{"q": "...", "answer": "...", "rationale": "..."}])

# задание-программа:
rb.task_heading(doc, "Задание 2. ...")
rb.body(doc, "Условие...")
rb.solution_heading(doc)
rb.add_code_block(doc, code_str, language="python")
rb.add_output_block(doc, output_str)
rb.explanation(doc, ["Абзац 1...", "Абзац 2..."])

# в конце (раздел сам начинается с новой страницы):
rb.control_questions(doc, [{"q": "...", "a": "..."}])

rb.save(doc, "labs/4/report.docx")
```

Структура отчёта: титульник → цель → задания по порядку → контрольные вопросы.
Не добавляй разделов, которых нет в задании (например, «Исходные данные» с
кодом вспомогательных модулей). Теоретическую часть методички в отчёт не
переписывай.

**Код в отчёте — только то, что относится к заданию.** Под заданием вставляй
лишь его функции, классы и методы, а не файлы целиком:

- вырезай фрагменты из реальных файлов через `ast` (по имени функции/класса,
  метод — как `Класс.метод` под заголовком `class Класс:`, вместе с
  декораторами), чтобы код в отчёте совпадал с файлами символ в символ;
- перед каждым блоком — подпись `Фрагмент файла <имя>:` (через
  `rb.body(..., indent=False)`), после кода — строка запуска
  (`Запуск: python main.py N`), затем вывод;
- общие помощники (форматирование, замер времени) показывай один раз — в
  первом задании, где они используются; если метод класса дописан в более
  позднем задании, показывай в этом задании только новые методы;
- для раскладки `src/taskK.py` файл обычно и есть фрагмент — вставляй его
  целиком.

Полный рабочий пример — `sample_report.py`. Запусти, чтобы увидеть эталон.

## Имя, группа, кафедра

Два способа, оба поддержаны:
- **Плейсхолдеры (по умолчанию):** не передавай `department`/`group`/
  `student_name` — в титульнике останутся `{{DEPARTMENT}}`, `{{GROUP}}`,
  `{{STUDENT_NAME}}`, впишешь вручную в Word.
- **Из конфига:** если есть `config.json` (скопируй из `config.example.json`) —
  прочитай его и передай значения в `title_page(...)`.
`config.json` — в `.gitignore` (личные данные не коммитим).

## Проверка (обязательно перед «готово»)

```bash
soffice --headless --convert-to pdf labs/<N>/report.docx --outdir labs/<N>/
pdftoppm -png -r 110 labs/<N>/report.pdf labs/<N>/preview
# открой preview-*.png и глазами сверь оформление
```
Если `soffice` нет, а на macOS установлен Microsoft Word — конвертируй через него:

```bash
osascript -e 'tell application "Microsoft Word"
  activate
  open POSIX file "/абсолютный/путь/labs/<N>/report.docx"
  delay 2
  set d to active document
  save as d file name "/абсолютный/путь/labs/<N>/report.pdf" file format format PDF
  close d saving no
end tell'
```

Если нет ни `soffice`, ни Word, ни `pdftoppm` — сообщи пользователю, но отчёт
всё равно собери (просто без авто-предпросмотра). После просмотра удали
`preview-*.png`.

## Правила

- Только стандартная библиотека Python в решениях, если не сказано иное.
- В `labs/<N>/` — только задание, код (структура из методички или
  `src/taskK.py`, + данные), отчёт и `EXPLAIN.md`. Никаких тестов, лишних
  модулей, скриптов сборки, файлов с сохранённым выводом.
- Структуру проекта, заданную методичкой, воспроизводить точно.
- В отчёте под заданием — только относящиеся к нему фрагменты кода.
- В коде решений — ни комментариев, ни докстрингов.
- Проверка — запуском в терминале; отчёт — только когда проверки проходят.
- Вывод в отчёте — реальный, из запуска, не больше страницы. Не выдумывать.
- Оформление отчёта — только через `report_builder.py`. XML/стили руками не трогать.
- Перед «готово» — рендер в PDF и визуальная проверка.
